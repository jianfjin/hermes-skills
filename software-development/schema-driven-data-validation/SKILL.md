# Schema-Driven Data Validation

Pattern for designing structured DSLs (domain-specific languages) where JSON Schema is the canonical definition, validators load the schema dynamically, and test data coexists across generated and curated layers.

## Core Principle

**The schema file is the source of truth.** Validator code loads the schema at runtime and delegates structural checks to `jsonschema`. This prevents drift between documentation and validation logic.

```text
schema.json (canonical DSL definition)
    ↕ loaded at runtime
validator.py (uses jsonschema.validate())
    ↕
rule instances (JSON data)
```

## Use Cases

- Rule engine DSLs (conditions + actions)
- Configuration file validation
- Plugin/filter grammars
- Any structured data format where the shape is too complex for hand-written checks

## Skill Structure

A schema-driven validation module has three layers:

### 1. Schema Definition (`schema.json`)

The schema formally defines:

- **Required vs optional fields** — JSON Schema `required`, `properties`, `additionalProperties: false`
- **Enums** — for constrained string values (rule types, operators)
- **Discriminated unions** — `oneOf` for variants (atomic condition vs compound vs empty)
- **Recursive references** — `$ref` for nested structures (compound conditions containing sub-conditions)
- **Nullables** — `type: ["string", "null"]` for optional nullable fields
- **Formats** — `format: "date"` for date strings
- **Patterns** — `pattern` regex for field naming conventions
- **Descriptions** — every field gets a `description` so the schema is self-documenting

**Key pattern — discriminated union with oneOf:**

```json
{
  "condition": {
    "oneOf": [
      { "$ref": "#/$defs/conditionCompoundAnd" },
      { "$ref": "#/$defs/conditionAtomic" },
      { "$ref": "#/$defs/conditionEmpty" }
    ]
  },
  "$defs": {
    "conditionCompoundAnd": {
      "type": "object",
      "required": ["and"],
      "properties": {
        "and": {
          "type": "array",
          "items": { "$ref": "#/$defs/condition" },
          "minItems": 1
        }
      },
      "additionalProperties": false
    },
    "conditionAtomic": {
      "type": "object",
      "required": ["field", "operator"],
      "description": "'value' required for all operators except 'exists'. Missing from required to allow exists-without-value.",
      "properties": {
        "field": { "type": "string", "pattern": "^[a-zA-Z_]" },
        "operator": { "type": "string", "enum": ["eq", "ne", "gt", "gte", "lt", "lte", "in", "not_in", "contains", "exists"] },
        "value": {}
      },
      "additionalProperties": false
    },
    "conditionEmpty": {
      "type": "object",
      "maxProperties": 0
    }
  }
}
```

### 2. Validator (`validator.py`)

The validator loads the schema and delegates structural checks:

```python
import json
import jsonschema
from pathlib import Path

SCHEMA_PATH = Path(__file__).parent / "schema.json"

def validate_bundle(bundle: dict) -> None:
    schema = json.loads(SCHEMA_PATH.read_text())
    try:
        jsonschema.validate(instance=bundle, schema=schema)
    except jsonschema.ValidationError as exc:
        path = " → ".join(str(p) for p in exc.absolute_path) if exc.absolute_path else "(root)"
        raise ValidationError(f"schema violation at {path}: {exc.message}")

    # Semantic checks beyond JSON Schema
    seen = set()
    for item in bundle.get("rules", []):
        rid = item["rule_id"]
        if rid in seen:
            raise ValidationError(f"duplicate rule_id: {rid}")
        seen.add(rid)
```

**Design decisions:**
- Schema covers structure (field presence, types, enums, nesting)
- Validator adds **semantic** checks (duplicates, referential integrity) that JSON Schema cannot express
- This split keeps the schema clean and the validator focused on business rules

### 3. Data Layer (generated + curated)

When working with large datasets, separate:

- **Generated data** — bulk fixtures (e.g., 1000 rules generated by script). Useful for volume testing but may have overlapping conditions that make exact-match tests impossible.
- **Curated data** — hand-crafted rules with known properties. These are the testable examples.

```text
fixtures/
├── wp8_data.json        ← 1000 generated rules + 6 curated rules
├── wp3_data.json        ← generated roadmap
└── wp2_data.json        ← generated stakeholders
```

**Merging strategy:** Append curated entries after generated ones. Keep a `source_doc_ref: "curated/..."` marker for identification.

## Testing Strategy

### Superset Check vs Exact Match

When test data is dense (many rules trigger for any input), use **superset checks** instead of exact matches:

```python
def check(state, must_contain):
    triggered = {r.rule_id for r in evaluator.triggered_rules(state, rules)}
    missing = set(must_contain) - triggered
    assert not missing, (
        f"Expected curated rules {sorted(must_contain)} to be triggered, "
        f"but {sorted(missing)} were missing. "
        f"Triggered {len(triggered)} rules total."
    )
```

**Superset check** — asserts `must_contain ⊆ triggered`. OK with extra rules.
**Exact match** — asserts `triggered == expected`. Requires sparsely overlapping conditions.

Use exact match when conditions are sparse and predictable (rule sets with <50 rules). Use superset check when conditions are dense (1000+ rules with overlapping conditions).

### Embedded Tests

Test cases can be embedded in the data file itself:

```json
{
  "rules": [...],
  "tests": [
    {
      "name": "test-01: high maturity triggers compound rule",
      "state": { "stakeholder_type": "biotech-sme", "answers": {...} },
      "expected_rule_ids": ["CURATED-RULE-001"]
    }
  ]
}
```

A `RuleLoader` can optionally run these on load. This is useful for data that comes from a stable source. However, if the data is generated and embedding precise test cases is impractical, either:
- Remove embedded tests (rely on schema structural validation only)
- Write separate test files with superset checks

## Pitfalls

- **Normalizer → constructor data loss (recurring pipeline bug).** When building a multi-stage data pipeline (schema → normalizer → constructor → domain model), every field added to the schema must be traced through ALL stages. The most common bug: a field is added to the schema (validation layer), mapped in the normalizer (transformation layer), but never read in the constructor (instantiation layer). The data is validated then silently discarded. This is a blind spot code review catches but solo implementation tends to miss. After adding a field to a schema, verify it reaches the domain model by searching for the constructor call site and tracing the end-to-end path. The same bug can appear in orthogonal pipelines: one adapter normalizes correctly while another hardcodes the default.
- **Date strings in JSON != Python date objects.** JSON Schema `format: date` validates string shape but does not parse into Python `date`. The adapter layer must call `date.fromisoformat(raw)` with a null guard. A `_parse_date` helper accepting `str | None` and returning `date | None` is the simplest pattern. Without it, date fields pile up as strings in domain models and break downstream `.isoformat()` calls.
- **`exists` operator does not need a value field.** When an atomic condition operator checks existence (`exists`), the comparison value is semantically meaningless. Make `value` optional in the schema's `required` list, or use `if/then` to conditionally require it. Tests should cover both `exists` with value and `exists` without value to ensure neither path crashes.
- **Schema structural validation != runtime correctness.** A schema that validates a date field as `format: date` only checks the JSON string looks like a date. It does NOT ensure the consuming code actually calls `date.fromisoformat()` and produces Python `date` objects. The schema is one layer; the constructor that builds domain models is a separate layer. Audit both independently.

- **Don't hand-write field checks in validator code.** If the schema says `"type": ["string", "null"]` but the validator accepts anything, the schema is a lie. Always use `jsonschema.validate()`.
- **Conflict detection overreach.** Two rules with identical `(rule_type, applies_to, condition)` tuples may appear conflicting, but if they exist in generated data, they are resolved by priority at runtime. Static conflict detection is too strict for overlapping conditions. Only flag truly identical `rule_id` values.
- **Test data specificity mismatch.** Generated test data often uses answer values that don't match the application's questionnaire schema. Always validate test state values against the real questionnaire options.
- **Schema is not a test runner.** Don't put test-case logic in the validator. Test suites belong in separate files, not embedded in the schema.
- **Nullable vs optional.** A field with `"default": null` in the schema description must still have `"type": ["string", "null"]` if JSON `null` is a valid input.
- **Recursive $ref loops.** Circular `$ref` chains in oneOf can cause stack overflow in some JSON Schema validators. Keep recursion depth to 1-2 levels.
- **Don't skip fixture tests silently.** If embedded tests don't pass, either fix the test data or remove the tests — don't add a `--skip-tests` flag that bypasses validation silently.

## Verification

After writing a schema + validator:

```python
# 1. Schema is valid JSON
import json
schema = json.loads(open("schema.json").read())

# 2. Schema validates a minimal bundle
bundle = { "version": "v1", "rules": [...], "tests": [] }
validate_bundle(bundle)

# 3. Schema catches invalid data
try:
    validate_bundle({ "version": 123 })  # wrong type for version
    assert False, "should have raised"
except ValidationError:
    pass

# 4. Semantic check catches duplicates
try:
    validate_bundle({ "version": "v1", "rules": [
        { "rule_id": "R1", ... },
        { "rule_id": "R1", ... },  # duplicate
    ], "tests": [] })
    assert False
except ValidationError:
    pass

# 5. Real data validates
with open("production_data.json") as f:
    validate_bundle(json.load(f))
```

## File Structure

```
rules/                    → module directory
├── schema.json           → canonical DSL definition
├── validator.py          → loads schema, structural + semantic checks
├── compiler.py           → transforms validated data into domain models
├── loader.py             → bundles above into a load pipeline
└── tests/
    └── test_curated.py   → superset-check tests for curated rules
```
