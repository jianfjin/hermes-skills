## Product Verdict (Steve Jobs)

> "This is shit. A user drops a PDF and gets six grep rules checking for 'hdab,' 'ethics,' and 'minimisation.' It's a keyword linter, not a compliance audit. The engine counts words; it doesn't understand law."

**The gap**: architecture doc promises "neuro-symbolic reasoning" — actual delivery is TF-IDF + regex keyword matching. No LLM reads the Index, crosses the Wiki, and argues compliance.

**What's needed for "insanely great"**: Replace the 6 hardcoded grep rules with an LLM agent that performs multi-hop reasoning across the three layers and produces cited, argued findings. Keyword matching is "better than nothing." Understanding is "insanely great."

## Fixes Applied (same session)

All 9 actionable issues (P0–P2) were fixed:

### P0 (immediate)
- pickle → JSON cache with vocabulary-only storage
- Duplicate `Art-66.md` renamed to `.md.bak`
- Shared `ehds_audit_engine.py` created; KB rules parsed and used

### P1 (before deploy)
- `_load_index_entries` cached with 5-minute TTL
- Case-sensitivity: `"SCC"` → `"scc"` in cross-border rule
- Code duplication eliminated: both servers import shared engine

### P2 (soon)
- Embedding engine self-contained (`_parse_frontmatter_safe`, no mcp_server import)
- Frontmatter uses `yaml.safe_load` with line-by-line fallback
- TF-IDF: `min_df=2, max_df=0.85`

### Cross-review findings (7 additional bugs, all fixed)
- `idf_` stored as Python list → wrapped in `np.array(dtype=np.float64)`
- Cache staleness: added `chunk_count` comparison before loading
- RULE_05 regex `.*?` → `.+` to prevent OR-clause truncation
- TTL-based cache invalidation on `_load_index_entries`
- Import exception handling with 503 fallback in API server

## Remaining Gap

The engine is now a **well-built keyword linter** — architecturally clean, secure, cached, with unified code. But it still does keyword matching, not reasoning. The "insanely great" version requires LLM-based multi-hop reasoning across the three layers.
